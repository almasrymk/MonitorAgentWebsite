# قرارات المعمارية (ADRs)

## ADR-001 — Modular Monolith بـ Clean Architecture
**القرار:** deployable واحد (`MonitorAgent.Api`) وجواه موديولات تحت `src/Modules/<Name>/`، كل موديول فيه Domain وApplication وInfrastructure وقاعدة بيانات schema خاصة بيه. الـ host بيجمّع الموديولات وبس. الموديولات مش بتلمس بعض غير عن طريق contracts (أو أحداث integration)، واختبارات المعمارية بتطبّق ده على أي assembly اسمه `MonitorAgent.Modules.*` أول ما الـ host يضيفه.

## ADR-002 — CQRS بدون مكتبة خارجية
**القرار:** dispatcher داخلي في `MonitorAgent.BuildingBlocks.Application` بدل MediatR (أصبحت برخصة تجارية). الـ pipeline: Logging (الأبعد) ثم Validation بـ FluentValidation. الـ validation بترجع `Result` بـ `VALIDATION_FAILED` لو نوع النتيجة `Result`، وإلا بترمي `ValidationException` وبتتحول لـ 400. الـ handlers `internal`، وكل command أو query ليه handler واحد بالظبط (اختبار معماري + فحص عند التشغيل).

## ADR-003 — Angular workspace واحد بـ 3 تطبيقات
**القرار:** workspace واحد في `web/` بالـ Angular CLI: `site` (الموقع العام بـ SSR عشان الـ SEO)، و`portal` (بوابة العميل)، و`admin` (لوحة الأدمن)، ومكتبة `shared`. التطبيقات بتبدأ بالعربي (RTL) والإنجليزي هيتضاف مع i18n. Nx ممكن يتضاف فوق نفس الـ workspace (`nx init`) لو احتجنا caching أو affected builds لما الكود يكبر.

## ADR-004 — التكامل مع LicensingPlatform
**القرار:** LicensingPlatform نظام منفصل ومش بنعدّل فيه من هنا. الموقع بيتكلم معاه عن طريق الـ HTTP API بتاعه بس، من خلال adapter في موديول واحد (ACL)، ومفيش أي مشاركة لقاعدة البيانات. أي عقد بين الاتنين بيتكتب ويتختبر هنا بـ contract tests.

## ADR-005 — تسجيل الدخول والجلسات والـ MFA
**القرار:** ASP.NET Core Identity جوه موديول `Identity` بقاعدة بياناته في schema اسمها `identity`. الجلسة cookie من نوع `__Host-` (HttpOnly، Secure، SameSite=Strict) مش JWT، عشان التوكن ما يبقاش متاح لأي JavaScript.
- **CSRF:** أي request بيغيّر حاجة لازم يبعت الـ header `X-XSRF-TOKEN`. الواجهة بتجيب التوكن من `GET /api/v1/auth/csrf` لما تفتح، وتاني بعد الدخول أو الخروج لأن التوكن مربوط بالمستخدم.
- **الباسورد:** 12 حرف على الأقل من غير قواعد تركيب (NIST 800-63B)، والحساب بيتقفل 15 دقيقة بعد 5 محاولات غلط.
- **منع كشف الحسابات:** التسجيل ونسيت الباسورد بيرجعوا نفس الرد سواء الإيميل موجود أو لأ، والدخول بإيميل مش موجود بياخد نفس الوقت ونفس الخطأ زي الباسورد الغلط.
- **الـ MFA:** TOTP مع recovery codes. حسابات الموظفين (Admin وSupport وFinance والمحتوى) ما تقدرش تدخل لوحة الأدمن غير بجلسة اتعملت بالـ MFA، وما تقدرش تقفله.
- **الجلسات:** تغيير الباسورد أو إعادة تعيينه أو "اخرج من كل الأجهزة" بيقفل الجلسات التانية، لأن الـ security stamp بيتراجع كل `Identity:SessionValidationSeconds` (60 ثانية افتراضيًا).
- **مفاتيح التشفير** (Data Protection) متخزنة في نفس قاعدة البيانات، عشان أكتر من نسخة من الـ API تقدر تقرا نفس الـ cookies.

## ADR-006 — حساب الشركة هو الـ tenant
**القرار:** كل عميل عبارة عن شركة (`CustomerAccount` في موديول `Customers`)، وكل حاجة بتاعة العميل (التراخيص والأجهزة والفواتير في المراحل الجاية) بتتربط بالـ id بتاعها.
- الشخص الواحد عضو في شركة واحدة بس (unique index على `Members.UserId`).
- مفيش أي endpoint بياخد company id. الشركة دايمًا بتتجاب من عضوية المستخدم اللي داخل، فمستحيل عميل يوصل لبيانات عميل تاني حتى لو خمّن ids. أي id لعضو أو دعوة مش في شركته بيرجع NOT_FOUND.
- الأدوار: Owner (بيدير الفريق)، وBilling، وTechnical، وViewer. لازم يفضل Owner واحد على الأقل.
- الدعوة بتتبعت بالإيميل وصالحة 7 أيام ومرة واحدة، ولازم تتقبل من حساب بنفس الإيميل. التوكن مش بيتخزن، بيتخزن الـ SHA-256 بتاعه بس.
- الموديولات التانية بتعرف بيانات المستخدم (الإيميل والاسم) عن طريق `IUserDirectory` في `Identity.Contracts`، مش من قاعدة بيانات Identity مباشرة.

## ADR-007 — الربط مع LicensingPlatform بحساب خدمة
**القرار:** موديول `Licenses` هو طبقة الحماية (ACL) الوحيدة اللي بتكلم LicensingPlatform. بيدخل بمستخدم مخصص للموقع (`Licenses:Platform:ServiceEmail` و`ServicePassword` من الأسرار)، وبيستخدم الـ endpoints الموجودة من غير ما نعدّل حاجة في LicensingPlatform.
- **ليه:** الـ client tokens في LicensingPlatform بتوصل لـ endpoints الأجهزة بس، ومفيش API للأنظمة التانية. لما يتعمل integration API هناك، هنغيّر الـ client بس، والشاشات والـ handlers مش هتتأثر.
- **الصلاحيات المطلوبة لحساب الخدمة:** catalog.read و customers.manage و subscriptions.manage و licenses.read و licenses.manage.
- **منع التكرار:** كل طلب له `OrderReference` فريد في جدول `licenses.Grants`. إصدار الرخصة بيتم على خطوات (عميل، اشتراك، رخصة)، وكل خطوة بتتحفظ. فلو حصل خطأ في النص، إعادة المحاولة بنفس الرقم بتكمّل من مكانها ومش بتعمل اشتراك تاني.
- **مفتاح المنتج:** LicensingPlatform بيرجّعه مرة واحدة بس. بنخزّنه متشفّر بـ Data Protection، وبيظهر للـ Owner والـ Technical بس، وكل مرة بيتشاف بتتسجل.
- **العزل:** الرخصة بتتجاب من LicensingPlatform وبعدين نتأكد إن الـ CustomerId بتاعها هو عميل شركة المستخدم، وإلا نرجّع LICENSE_NOT_FOUND.
- **قائمة الأسعار:** الخطط المنشورة والمدفوعة والحالية بس، وبتتخزّن 5 دقايق. ولو LicensingPlatform وقع، بنعرض آخر نسخة.
- **مخاطرة معروفة:** لو LicensingPlatform أصدر الرخصة واحنا وقعنا قبل ما نحفظها، إعادة المحاولة هتصدر رخصة تانية على نفس الاشتراك. ده بيتقفل لما LicensingPlatform يقبل مفتاح idempotency.

## ADR-008 — الدفع بصفحة مزوّد الدفع وإشعارات موقّعة
**القرار:** موديول `Commerce` فيه الطلبات والدفع والفواتير والدفتر. العميل بيدفع في صفحة مزوّد الدفع (hosted checkout)، فبيانات الكارت عمرها ما بتعدّي على سيرفراتنا، وده بيخلّينا في أبسط مستوى من PCI DSS (SAQ A).
- **المزوّد:** واجهة `IPaymentGateway` (إنشاء checkout، وقراءة الإشعار والتحقق من توقيعه). دلوقتي فيه `sandbox` للتطوير والاختبارات بس، والموقع بيرفض يشتغل بيه برّه Development. Paymob أو Stripe بيتضافوا كـ adapter من غير ما حاجة تانية تتغيّر.
- **الإشعارات (webhooks):** `POST /api/v1/payments/notifications/{provider}` من غير session ولا CSRF. التوقيع بيتراجع الأول قبل أي حاجة، ولو غلط نرجّع 401.
- **منع التكرار:** كل إشعار بيتسجل في `commerce.ProcessedNotifications` بمفتاح (المزوّد، رقم الحدث). الإشعار المكرر بياخد 200 ومش بيعمل حاجة. ولو اتنين وصلوا مع بعض، واحد بس بيتحفظ والتاني بياخد 503 فالمزوّد يبعته تاني. وفيه فاتورة واحدة بس لكل طلب (unique على OrderId)، وإصدار الرخصة نفسه idempotent برقم الطلب (ADR-007). يعني إشعار مكرر عمره ما يعمل رخصتين.
- **المبلغ:** الطلب بيتعلّم مدفوع بس لو المبلغ والعملة مطابقين بالظبط لسعر الطلب.
- **بعد الدفع:** سطر في الدفتر، وفاتورة برقم متسلسل من غير فراغات (`INV-yyyy-nnnnnn`)، وبعدين إصدار الرخصة. لو LicensingPlatform واقع، الطلب بيفضل `Paid` وفيه worker بيعيد المحاولة كل دقيقة (`Commerce:FulfillmentRetrySeconds`).
- **الصلاحيات:** الشراء للـ Owner والـ Billing بس. الأدمن يقدر يسجّل دفع يدوي (تحويل بنكي مثلًا) ويشوف كل الطلبات.
- **لسه:** الاسترداد (refund)، والتجديد، والمطابقة الليلية مع المزوّد، بعد اختيار المزوّد.

## ADR-009 — الإصدارات: الموقع بيتحقق من التوقيع ومبيوقّعش
**القرار:** موديول `Releases` بيخزّن كل إصدار من برنامج Monitor Agent ويعرض الـ manifest اللي البرنامج بيقراه. التوقيع بيتعمل برّه الموقع بأداة `tools/UpdateSigner` اللي في UBGMonitor، والمفتاح الخاص عمره ما بيوصل للسيرفر.
- **ليه:** لو حد اخترق الموقع، ميقدرش ينزّل تحديث مزيّف لأجهزة العملاء، لأن البرنامج مش بيقبل غير manifest موقّع بالمفتاح المتبني جواه.
- **رفع إصدار:** الأدمن بيرفع `manifest.json` (بالـ bytes بتاعته زي ما هي، base64) و`manifest.json.sig`. الموقع بيتأكد من التوقيع بالمفتاح العام (`Releases:PublicKey`) الأول، وبعدين بيتأكد من الـ manifest بنفس قواعد البرنامج: المنتج MonitorAgent، ورقم إصدار صحيح، وكل package ليها رابط https وsha256 وحجم. الإصدار بيبدأ مسودة.
- **النشر:** مفيش غير إصدار أحدث من الحالي ينفع يتنشر. `GET /updates/manifest.json` و`.sig` بيرجّعوا أحدث إصدار منشور على قناة stable بالظبط زي ما اتوقّع، و`/updates/{channel}/...` للقنوات التانية زي beta. ده هو الـ `Updates:ManifestUrl` اللي البرنامج هيتظبط عليه.
- **السحب:** لو إصدار طلع فيه مشكلة، سحبه بيرجّع الإصدار اللي قبله. الأجهزة اللي نزّلته بتفضل عليه، لأن البرنامج مش بيرجع لإصدار أقدم.
- **الملفات نفسها:** بتتحط على أي استضافة https (CDN أو storage). الموقع بيخزّن روابطها والـ hash بتاعها بس.

## ADR-010 — الواجهات: لغتين، ومكتبة مشتركة، وفحص وصول تلقائي
**القرار:** التلات تطبيقات (الموقع، والبوابة، ولوحة الأدمن) بيستخدموا مكتبة `shared` فيها الاتصال بالـ API، والترجمة، وتنسيق الفلوس والتواريخ، والستايل الأبيض والأسود.
- **اللغة:** عربي (RTL، الافتراضي) وإنجليزي (LTR). الموقع العام عناوينه `/ar/...` و`/en/...` عشان كل لغة تتفهرس لوحدها. الستايل كله بـ logical properties فبيتقلب لوحده. أي نص ناقص في لغة من الاتنين بيوقّع الـ build.
- **العرض على السيرفر:** الصفحات الثابتة بتتبني مقدمًا. الأسعار والتحميل بيتعرضوا على السيرفر مع كل طلب من الـ API، فدايمًا محدّثين، والمتصفح بيستخدم نفس البيانات من غير ما يطلبها تاني.
- **نفس الـ origin:** الـ API والتطبيقات تحت نفس الدومين (`/api` و`/portal` و`/admin` ورا reverse proxy)، لأن كوكيز الجلسة `__Host-`.
- **الأسعار:** بتتعرض زي ما الكتالوج بيرجّعها، ومفيش حسابات فلوس في المتصفح.
- **الجودة:** اختبارات Playwright على الكمبيوتر والموبايل، وكل صفحة بتتفحص بـ axe (WCAG 2.2 AA) باللغتين. لازم يبقى مفيش أي مخالفة.
- **البوابة ولوحة الأدمن:** تطبيقات في المتصفح بس (من غير SSR)، لأن كل صفحاتها بعد الدخول ومش محتاجة فهرسة. اللغة المختارة بتتحفظ في المتصفح. أي صفحة بعد الدخول بتتأكد من الجلسة الأول، واللي مش داخل بيروح لصفحة الدخول ويرجع لنفس الصفحة بعدها (روابط داخلية بس). مفتاح المنتج مش بيظهر غير لما العميل يطلبه.
- **لوحة الأدمن:** للموظفين بس. الموظف اللي من غير تحقق بخطوتين بيتحوّل لصفحة الحساب يشغّله، وبعدين يدخل تاني بالكود، لأن الـ API بيطلب جلسة اتعملت بالخطوة التانية. الإصدارات بتترفع زي ما هي بالظبط (الملف والتوقيع)، والموقع عمره ما بيوقّع. صفحات الدخول والحساب والإطار مشتركة بين البوابة والأدمن في مكتبة `shared`.

## ADR-011 — الدعم: التذاكر والاقتراحات
**القرار:** موديول `Support` جديد (schema `support`) فيه التذاكر بمحادثتها، والاقتراحات.
- **مين يشوف إيه:** أي عضو في الشركة يقرا تذاكرها، وكل الأدوار تكتب ما عدا Viewer. موظفين الدعم والأدمن (بتحقق بخطوتين) يشوفوا كل التذاكر. تذكرة شركة تانية بترجع "مش موجودة" بالظبط زي تذكرة مش موجودة فعلًا، عشان مايتعرفش وجودها.
- **الحالات:** Open (مستنية الدعم) و Answered (مستنية العميل) و Closed. رسالة جديدة من العميل بتفتح التذكرة المقفولة تاني.
- **الإيميل:** لما الدعم يرد، صاحب التذكرة بياخد إيميل فيه رقم التذكرة والرابط بس، من غير نص الرد، فالمحتوى يفضل ورا الدخول. لو الإيميل فشل الرد بيتحفظ عادي.
- **الأمان:** النص بيتخزن ويرجع زي ما اتكتب، والواجهات بتعرضه كنص عمرها ما بتعرضه كـ HTML. حد أقصى 20 تذكرة مفتوحة للشركة و200 رسالة للتذكرة. المرفقات مؤجلة لحد ما يبقى فيه فحص فيروسات للملفات.
- **أسماء الموظفين:** العميل بيشوف الاسم الأول للموظف بس ومعاه "(Support)".

## ADR-012 — المحتوى: صفحات الموقع بالنسخ والمراجعة
**القرار:** موديول `Content` جديد (schema `content`) فيه الصفحة (Page) وكل نسخها (PageVersion)، بالعربي والإنجليزي ومعاهم وصف الـ SEO.
- **المسار:** المحرر (ContentEditor أو Admin) بيكتب مسودة ويبعتها للمراجعة. المراجع (ContentReviewer أو Admin) يا ينشرها يا يرجّعها بسبب مكتوب. آخر واحد عدّل النسخة مايقدرش يوافق عليها ولا يرفضها، حتى لو أدمن. فيه نسخة واحدة بس مفتوحة (مسودة أو في المراجعة) في أي وقت، والنسخ القديمة بتفضل للتاريخ وممكن تسترجع أي واحدة كمسودة جديدة.
- **التزامن:** كل خطوة بتغيّر `UpdatedAt` وهو concurrency token، فلو اتنين اشتغلوا على نفس الصفحة في نفس اللحظة التاني بياخد `PAGE_CHANGED` بدل ما يكتب فوق التاني أو ينشر نص ماحدش راجعه.
- **الأمان (XSS):** النص مش HTML. هو markdown صغير (عناوين، قوائم، عريض، روابط) والواجهة بتحوّله لعناصر بنفسها ومابتستخدمش innerHTML أبدًا، فأي tag بيظهر كنص. الروابط مسموحة بس لـ https أو مسار جوه الموقع أو mailto.
- **الموقع:** `GET /api/v1/content/pages/{slug}` بيرجّع المنشور بس، مع cache دقيقة. الموقع بيعرض أي صفحة على `/{lang}/pages/{slug}` (SSR، و404 حقيقي لو مش منشورة). الصفحات اللي اسمها terms و privacy و refunds بتحل محل النص المكتوب في الكود، ولو مفيش نسخة منشورة النص الأصلي بيفضل.
- **مؤجل:** رفع الصور والملفات (MediaAsset) لحد ما يبقى فيه فحص فيروسات، وقوائم التنقل من الـ CMS.

## ADR-013 — العملاء والتقارير المالية في لوحة الأدمن
**القرار:** صلاحيتين جداد: `Staff.Finance` (المالية والأدمن) و`Staff.Customers` (الأدمن والدعم والمالية)، وكلهم بالتحقق بخطوتين.
- **العملاء:** الموظفين يدوروا على الشركة بجزء من الاسم أو بإيميل حد فيها بالظبط، ويشوفوا أشخاصها ودعواتها المفتوحة ورخصها، للقراية بس. القراية دي بتعدّي على `IStaffCompanyReader` منفصل عن مستودع العميل، عشان كود العميل يفضل مالوش أي طريقة يوصل بيها لشركة غير شركته.
- **الطلبات:** بقت للمالية كمان مش للأدمن بس (هما اللي بيسجلوا التحويلات البنكية)، وفيها اسم الشركة وفلتر بالشركة. إصدار رخصة يدوي من صفحة العميل للأدمن بس.
- **التقارير:** من دفتر الحركات (Ledger) مش من الطلبات، يعني الفلوس اللي اتحركت فعلًا: الصافي لكل عملة (المدفوعات ناقص المسترد)، وحسب الشهر والخطة وطريقة الدفع. عملات مختلفة عمرها ما بتتجمع. الأيام بتوقيت UTC، وأقصى فترة 3 سنين.
- **CSV:** ملف بكل حركة. أي خلية بتبدأ بـ = أو + أو - أو @ بيتحط قبلها ' عشان Excel مايشغّلهاش كمعادلة (أسماء الشركات بيكتبها العملاء). الملف فيه BOM عشان العربي يظهر صح في Excel.

## ADR-014 — سجل التدقيق
**القرار:** موديول `Audit` (schema `audit`) فيه سطر لكل خطوة حساسة: مين عملها، وامتى، ومن أنهي IP، وعلى إيه، والسبب أو المرجع لو موجود.
- **إزاي بيتكتب:** أي command بيعمل `IAuditedCommand` بيتسجل تلقائيًا من الـ pipeline بعد ما الـ handler ينجح بس، فالمحاولة المرفوضة عمرها ما تتكتب كأنها حصلت. ده بيغطي: تسجيل دفع يدوي، إلغاء طلب، إصدار رخصة، إظهار مفتاح المنتج، تصفير جهاز، رفع ونشر وسحب الإصدارات، إنشاء صفحة ومراجعتها واسترجاع نسخة، قفل التذاكر والرد على الاقتراحات، وتغييرات فريق العميل.
- **لو الكتابة فشلت:** التغيير نفسه بيكون اتحفظ خلاص، فبنسجل Error في اللوج بدل ما نرجّع للمستخدم إن العملية فشلت (عشان مايعيدهاش مرتين).
- **القراية:** للأدمن بس، بفلتر حسب المجال (أول جزء من اسم العملية) أو الشخص أو الهدف. مفيش أي endpoint بيعدّل أو يمسح سطر.
- **الموديول طبقتين بس** (Application و Infrastructure) لأنه سجل مش فيه قواعد Domain.
- **الصحة:** `/health/ready` بقى بيتأكد إن قاعدة البيانات بترد، و `/health/live` من غير فحوصات.


## ADR-015 — التقوية قبل الإطلاق: الهيدرز، والسرعة، والفحص الأمني
**القرار:**
- **الموقع (SSR):** ضغط الردود (gzip/brotli)، وCSP صارمة بـ nonce جديد مع كل طلب لكل `<script>`، من غير `unsafe-inline` للسكريبتات. الاستثناء الوحيد هو hash للـ handler اللي Angular بيحطه عشان يحمّل الـ CSS من غير ما يوقّف العرض. ومعاها `frame-ancestors 'none'` و nosniff و Referrer-Policy و Permissions-Policy و COOP، ومن غير `X-Powered-By`.
- **صفحات المحتوى:** بتتحمل بـ route resolver قبل العرض، فالمتصفح بيكمّل نفس اللي السيرفر عرضه من غير ما الصفحة تتهز (CLS = 0).
- **Lighthouse في الـ CI:** على 5 صفحات، 3 مرات لكل صفحة. الـ build بيفشل لو الأداء أقل من 90، أو الوصولية أقل من 95، أو LCP أكتر من 2.5 ثانية، أو CLS أكتر من 0.1. محليًا الأداء طلع 98-99 و LCP حوالي 1.7 ثانية.
- **الاعتماديات:** Dependabot كل أسبوع لـ NuGet و npm و Actions و Docker. Trivy بيفحص صورة الـ API في كل CI ويوقّع الـ build على أي ثغرة CRITICAL أو HIGH ليها حل. وفيه SBOM (SPDX) بيترفع مع كل build.
- **DAST:** OWASP ZAP كل ليلة (وكمان عند الطلب) على الـ API كله من ملف OpenAPI، على نسخة compose بباسورد عشوائي. أي تنبيه High بيوقّع الـ workflow.
- **الحمل:** سكريبت k6 في `tests/load` للتحديثات من البرامج، والزوار، وموجة إشعارات دفع موقّعة. الأهداف: p95 أقل من 300ms (و150ms لملف التحديثات)، والأخطاء أقل من 0.1%. بيشتغل عند الطلب من GitHub، والأرقام اللي بيُعتمد عليها بتكون من staging.
- **مش هنا:** اختبار الاختراق الخارجي والتحويل للدفع الحقيقي محتاجين موافقة مكتوبة من صاحب المشروع (شوف قائمة الإطلاق).

## ADR-016 — بيانات العميل: التنزيل والمسح
**القرار:** كل موديول بيخزّن حاجة عن الأشخاص بيسجّل `IPersonalDataSource` (في BuildingBlocks)، وIdentity بيسأل كلهم. موديول جديد بيضيف واحد بس من غير ما يتغير حاجة تانية.
- **التنزيل:** `GET /api/v1/account/export` بيرجّع ملف JSON فيه الحساب، وعضوية الشركة والدعوات اللي جت على بريده، والطلبات اللي عملها، ورسايله في الدعم واقتراحاته، وسجل الدخول، والخطوات الحساسة اللي عملها. من غير cache، ومحدود بنفس حد محاولات الدخول.
- **المسح:** `POST /api/v1/account/delete` بكلمة السر تاني. الحساب بيفضل بنفس الـ id بس اسمه وبريده بيتبدلوا، وكلمة السر والتحقق بخطوتين بيتشالوا، والحساب بيتقفل للأبد ويخرج من كل مكان. البريد بيبقى متاح لحساب جديد. بيتبعت إيميل تأكيد على البريد القديم.
- **اللي بيتشال:** عضويته في الشركة، وبريده من أي دعوة، وعناوين الـ IP من سجل الدخول وسجل التدقيق.
- **اللي بيفضل:** الطلبات والفواتير والمدفوعات (القانون الضريبي بيطلبها، وهي باسم الشركة مش الشخص)، وتذاكر الدعم (تاريخ الشركة، وكاتبها بيظهر "Deleted user")، وسطور التدقيق نفسها (لازم تفضل كاملة).
- **الشروط:** المالك الوحيد لفريق فيه ناس تانيين لازم يخلّي حد مالك الأول (`LAST_OWNER`). لو هو العضو الوحيد، الشركة بتفضل من غير أعضاء عشان رخصها وفواتيرها. حسابات الموظفين مش بتتمسح من صاحبها (`STAFF_ACCOUNT`)، الأدمن هو اللي بيقفلها.

## ADR-017 — بوابات الجودة في الـ CI
**القرار:** الحاجات اللي خطة الاختبارات طالبها بقت بتوقّف الـ build لوحدها، مش بتتراجع بالإيد.
- **التغطية:** `scripts/ci/coverage-gate.py` بيقرا تقرير الـ backend ويوقّع الـ build لو تغطية سطور الـ Domain والـ Application (ومعاهم SharedKernel) أقل من 80%. دلوقتي 92%. المكتبة المشتركة في الواجهات حدها 70% (في `angular.json`)، ودلوقتي 95%. الصفحات نفسها متغطية بـ Playwright (200 اختبار على الكمبيوتر والموبايل) مش باختبارات وحدة، فمفيش حد تغطية عليها.
- **SQL Server حقيقي:** job في الـ CI بيشغّل نفس اختبارات الـ API على SQL Server 2022 بالـ migrations الحقيقية، كل class في قاعدة لوحدها وبتتمسح بعدها. بيتفعّل بمتغير `TEST_SQLSERVER`، ومن غيره الاختبارات بتشتغل على SQLite زي الأول. ده بيمسك اللي SQLite مش بيشوفه: الـ migrations، والـ collation، وأنواع الأعمدة.
- **عقد الـ OpenAPI:** نسخة محفوظة من ملف الـ API في `tests/MonitorAgent.Tests/Contract`. الاختبار بيفشل لو endpoint اتشال، أو schema أو خاصية اتشالت، أو خاصية بقت مطلوبة. أي تغيير تاني لازم يتسجل في النسخة (`UPDATE_OPENAPI_SNAPSHOT=1`) عشان يبان في الـ PR.
- **Semgrep:** قواعد C# و TypeScript والأسرار والـ Actions. أي نتيجة بدرجة ERROR بتوقّع الـ build.
- **الـ Actions:** كل action متثبّت على commit SHA (والإصدار جنبه في تعليق)، عشان tag يتنقل ما يغيّرش اللي بيشتغل عندنا. Dependabot بيحدّثهم.
